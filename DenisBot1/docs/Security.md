# Avaterra Bot - Security Baseline

## 1. Политика хранения секретов
- Запрещено хранить токены/пароли/API-ключи в `.txt`, `README`, `docs` и коде.
- Все секреты хранятся только в:
  - переменных окружения на сервере;
  - secret storage (рекомендуется: Vault/1Password Secrets/GCP Secret Manager).
- В репозитории допускается только файл `.env.example` с пустыми значениями.

## 2. Обязательная ротация ключей
- При обнаружении секрета в открытом виде ключ считается скомпрометированным.
- Немедленные шаги:
  1. Выпустить новый ключ у провайдера.
  2. Обновить секрет в secret storage/ENV.
  3. Перезапустить сервис.
  4. Проверить, что старый ключ деактивирован.
- Периодическая ротация:
  - `BOT_TOKEN`: раз в 90 дней.
  - `DEEPSEAK_API_KEY`: раз в 90 дней.
  - `KIE_API_KEY`: раз в 90 дней.
  - `DB_PASSWORD` и `REDIS_PASSWORD`: раз в 60 дней.

## 3. Политика логирования
- Нельзя логировать:
  - токены;
  - пароли;
  - API-ключи;
  - полные payload с персональными данными.
- Обязательно маскировать поля:
  - `Authorization`;
  - `api_key`;
  - `token`;
  - `password`;
  - `secret`.
- Формат журналов:
  - `timestamp`, `service`, `request_id`, `operation`, `status`, `latency_ms`, `error_code`.

## 4. Контроль доступа
- Команды администратора доступны только `ADMIN_TELEGRAM_IDS`.
- Webhook должен проверять `X-Telegram-Bot-Api-Secret-Token`.
- Доступ к серверу только по SSH-ключам, вход по паролю отключить.
- Использовать минимально необходимые права для сервисных аккаунтов.

### Текущее состояние SSH-доступа
- Локальный ключ агента: `~/.ssh/avaterra_deploy_ed25519` (ed25519, без passphrase).
- Алиас в `~/.ssh/config`: `Host avaterra` -> `root@<server>`.
- Public key установлен в `/root/.ssh/authorized_keys` на сервере.
- Файл `Ssh.txt` с паролем удалён из репозитория.
- Действия владельца:
  - сменить пароль `root` (он был передан в открытом виде);
  - после проверки ключевой авторизации отключить `PasswordAuthentication`
    и `ChallengeResponseAuthentication` в `/etc/ssh/sshd_config`.

## 5. Защита от дублей и повторной отправки
- Каждая публикация имеет `idempotency_key`.
- Для планировщика и публикации использовать distributed lock (Redis).
- Повторные задачи обрабатываются как `no-op`, если публикация уже выполнена.

## 6. Fail-safe при сбоях внешних API
- Retry policy: exponential backoff + jitter.
- Circuit breaker для DeepSeak и KIE.
- При недоступности генерации:
  - использовать fallback-шаблоны;
  - уведомлять администратора;
  - не публиковать пустой/дефектный контент.

## 7. Минимальный чеклист перед продакшеном
- [ ] Секреты удалены из всех текстовых файлов и истории изменений.
- [ ] Ключи, ранее опубликованные в открытом виде, ротированы.
- [ ] Включена маскировка секретов в логах.
- [ ] Включен webhook secret token.
- [ ] Включен allowlist администраторов.
- [ ] Проверена идемпотентность публикаций.
