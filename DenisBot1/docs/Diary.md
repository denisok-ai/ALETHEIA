### Наблюдения

- `last_error=quality:<codes>` на провале; на успехе сбрасывается. Extra pass читает это как feedback.

- Решено (2026-08-18): выкат на прод `/opt/avaterra-bot`; `.env` — `DEEPSEEK_MAX_TOKENS=2048`, `WEEKLY_PIPELINE_EXTRA_PASSES=2`.

## [2026-07-27] Частичный weekly pipeline 6/7: draft не ретраится

### Наблюдения
- Админ-уведомление: «Контент на неделю собран частично», неделя 27.07–02.08, `Готово: 6/7`, `проходов: 2`, `plan_id=4a5443d5-…`.
- На Tue 28.07 `[pain]` две строки: `draft: draft be4092af` и `missing: нет готового поста на этот день`.
- `last_error` у item пустой → статус так и остался `draft` после pass1 (генерация не дошла до `update_item_text` / `quality_failed` / `failed`).

### Корень
1. В `_run_single_pass` исключение из `prepare_item` ловится, логируется и `continue` — статус item **не меняется**, остаётся `draft`.
2. Pass2 ретраит только `quality_failed|failed|dedup_blocked|text_ready`, **но не `draft`** → застрявший draft в том же прогоне больше не обрабатывается.
3. Типичный триггер: сетевой timeout / `aiohttp.ClientError` после исчерпания retry DeepSeek (не всегда заворачивается в `DeepSeekError`), либо сбой до записи статуса.
4. `_verify_plan` дублирует проблему дня: и non-ready item, и синтетический `missing`.

### Решение
- Pass2/extra включает `draft` в retry-статусы.
- При exception в проходе — `update_item_status(..., failed, last_error=...)`.
- DeepSeek: retry на `TimeoutError`, финальные сетевые ошибки → `DeepSeekError`.
- `missing` в сверке только если на день **нет ни одного** item.
- Тесты на retry draft и mark-failed.

### Решено / Открыто
- Решено: один сбой LLM/сети в pass1 больше не оставляет «немой» draft до ручного перезапуска.
- Открыто: устойчивый `quality_failed` (например `too_long` у faq) по-прежнему даёт частичный итог — нужен fallback темы/шаблона (см. Diary 2026-05-18).

## [2026-05-18] Слово «метод» в посте 18.05: regex без падежей и страховка в публикаторе

### Наблюдения
- Заказчик: «в последнем посте опять вместо Школы фигурирует слово Метод. Сделай правило, чтобы слово метод в постах не фигурировало». В тексте сегодняшнего `educational` (id `5a8e95ad…`) — «**В методе** Аватэрра мы не работаем с диагнозами». Гейт `method_word` уже был добавлен 09.05.2026, но почему-то не сработал.
- В коде стоял `\\bметод\\b` (IGNORECASE). После «метод» в строке «методе» идёт буква «е» (word-char), поэтому правая граница слова не находится и regex не матчит. Тот же баг проигнорировал бы «методу», «методом», «метода», «методы», «методов», «методам», «методами», «методах». Промпт для LLM правило содержал, но без поддержки гейтом модель периодически срывается.
- Дополнительно: в БД на 21.05 (`author`, id `8edb0cb8…`) уже лежит ready-пост с «методы регресса» — он тоже пролез бы.

### Решение
- `services/quality/gates.py`: `_METHOD_WORD_PATTERN` расширён до `\\bметод(?:а|у|ом|е|ы|ов|ам|ами|ах)?\\b` (IGNORECASE). Покрывает все падежные формы ед./мн. числа и при этом не задевает производные `методик-`, `методическ-`, `методист-`, `методолог-` (после стема следует не-окончание из списка, граница не находится).
- `services/quality/gates.py`: новый `scan_publish_blockers(text)` — подмножество «красных» гейтов (FAQ, «калибр…», «метод», латиница Avaterra), запускается уже на этапе публикации. Brand profile не нужен.
- `services/publisher/channel_publisher.py`: `publish_item` после `normalize_post_lexicon` гонит `scan_publish_blockers`. При попадании пост уходит в `quality_failed` с `last_error=publisher_blocked:<codes>`, в логи летит ERROR `publisher_blocked_by_red_gate`, в `integration_logs` пишется `status=blocked`. В канал ничего не уходит. Это вторая линия защиты на случай «правила обновили после генерации, а в БД лежит старый ready-пост».
- `workers/content_worker.py`: `run_publisher_preflight` дополнительно сканирует уже `ready/approved` item'ы тем же `scan_publish_blockers`. При нарушении — `reset_item_for_regeneration` + `prepare_item`. В отчёте появилось поле `forced_reset` с id таких постов.
- `services/generator/prompts.py`: правило для LLM переписано — теперь явно перечислены все запрещённые падежные формы; добавлены позитивные подсказки («в школе», «по подходу школы»).
- `tests/test_quality_gates.py`: добавлены параметризованные тесты на 11 падежных форм «метод» (все обязаны падать в `method_word`) и 7 производных (`методика`, `методический`, `методически`, `методист`, `методология` — должны проходить). Плюс 3 теста на `scan_publish_blockers` (одиночный, чистый, полный «красный» набор).
- Прод: пост 21.05 (`author`) сброшен в `draft` руками — пересоберётся в ближайший `prepare`/preflight. Опубликованный 18.05 трогать не будем (см. договорённость в Diary 13.05: «метод» автоматически не правим, иначе ломаем падежи).

### Решено / Открыто
- Решено: regex покрывает все падежи, не задевая «методика»/«методология». Тесты этому посвящены.
- Решено: даже если LLM снова прорвётся с «методе», публикатор это поймает и пост в канал не уйдёт.
- Решено: preflight видит проблему в ready-постах из БД и переподготавливает их, поэтому день не теряется из-за обновления правил.
- Открыто: «метод» автоматически нормализовать (`метод → школа`) не пытаемся — без морфологического согласования получается коряво. При желании можно прикрутить `pymorphy3` и сделать падежно-корректную замену; пока полагаемся на регенерацию.

## [2026-05-18] Автономный публикатор: env-reconcile, preflight и startup catch-up

### Наблюдения
- После аудита `runtime_toggle` мы видим, кто включил `dry_run`, но автономности это не даёт: если переключение случилось в середине дня, посты не выйдут вплоть до перезапуска контейнера. Заказчик хочет: «посты должны выходить ежедневно в 11:00 МСК без вмешательства человека».
- Слабые места, помимо `runtime_toggle`: `misfire_grace_time=3600` (даунтайм >1 ч около слота — день потерян); деплой/рестарт сразу после 11:00 — APScheduler уже отстрелил миссфайр; недельный пайплайн оставляет `faq`/`reflection` в `draft/quality_failed/text_ready` (история 15.05) — Publisher молча пропускает.

### Решение
- `workers/content_worker.py`: новый `_reconcile_publisher_flags(settings)` сверяет в памяти `dry_run`/`enable_auto_publish` со значениями из `DRY_RUN`/`ENABLE_AUTO_PUBLISH` в окружении. Если есть дрейф (например, кто-то нажал `adm:dry`) — флаги возвращаются к окружению, и пишется WARNING `publisher_flags_reverted`. Это «жёсткий якорь»: даже если админ забыл выключить тестовый режим, перед каждым слотом всё откатывается к рабочему состоянию.
- `workers/content_worker.py`: `run_publisher_preflight(...)` дотягивает сегодняшние item'ы до публикабельного состояния. Сценарии: `text_ready` → `complete_image_for_item`; `quality_failed/failed/dedup_blocked` → `reset_item_for_regeneration` + `prepare_item`; `draft` → `prepare_item`. По каждому item'у — структурированный WARNING `publisher_preflight_outcome` с `from_status`/`to_status`. Если LLM/KIE упали — `publisher_preflight_item_failed` с трейсом, но слот всё равно идёт дальше.
- `_run_publisher_slot` теперь общий путь и для cron'а, и для startup-catchup: reconcile → state → preflight → `publish_due_today` → итог. Источник помечается полем `source` (`cron`/`startup_catchup`).
- `_maybe_schedule_startup_catchup(...)`: при старте бота, если по `settings.timezone` сейчас уже после `PUBLISH_HOUR:PUBLISH_MINUTE` и сегодня — публикационный день, через 60 секунд после регистрации крона добавляется одноразовый `DateTrigger` slot. Покрывает деплой/рестарт сразу после 11:00 без расчёта на misfire.
- `misfire_grace_time` для `content_publisher_daily` поднят с 3600 до 21600 (6 часов). Если бот лежал утром, APScheduler сам отстреляет слот при подъёме.
- Тесты `tests/test_publisher_autonomy.py` (9 кейсов): парсинг `_env_bool` (truthy/falsy/missing), отсутствие drift'а, реверт `dry_run`, реверт `enable_auto_publish`, оба сразу, и допустимая ситуация «`.env` сам в dry_run».
- `PYTHONPATH=src pytest -q` — **139 passed**.

### Решено / Открыто
- Решено: «жёсткий якорь» через `.env`. Если оператор хочет дольше держать `dry_run` — меняет `.env` и редеплоит. Это даёт детерминированное автономное состояние.
- Решено: preflight — последний шанс. Делаем не больше одной попытки восстановления на item; LLM-цикл `prepare_item` сам уважает `CONTENT_GENERATION_RETRY_MAX`.
- Открыто: если `faq` устойчиво ловится `too_long` (история 15.05), preflight потратит токены впустую и опять оставит `quality_failed`. Стоит позже добавить fallback по `theme_pool` (подбор соседней темы того же `post_type`/`audience`), но это уже не критическое.
- Открыто: общий план «деградаций» (нет KIE → текстовый пост без картинки) — отдельная задача, сейчас отсутствие картинки = `failed`, preflight не починит.

## [2026-05-18] Тихий `dry_run` 15–17 мая и аудит runtime-флагов

### Наблюдения
- Заказчик: «не вышли посты в пятницу, субботу и воскресенье». Поднял логи контейнера `avaterra-bot` за 14–17 мая и срез `content_items` за неделю 2026-05-11.
- 14 мая (`author`) штатно ушёл в канал (`published=1`). 15 мая `publisher_run_empty` — на дату не было ни одного `approved/ready` item'а. 16 и 17 мая в логах `publisher_dry_run` для одного item'а в день; в `integration_logs` reason помечен `dry_run_or_disabled`, а `channel_id` пришёл строкой, тогда как успешные публикации до этого писали его числом — то есть сработал именно dry_run-путь в `publish_item`.
- Состояние `.env` и контейнера: `DRY_RUN=false`, `ENABLE_AUTO_PUBLISH=true`, `TARGET_CHANNEL_ID` задан, контейнер не перезапускался с 13 мая. Значит ENV не менялся, но `settings` в памяти процесса жил «по-своему».
- Корень причины 16–17.05: в `bot/handlers/admin.py` есть команды `/dry_run on|off`, `/auto on|off` и inline-кнопки `adm:dry`, `adm:auto`, которые меняли `get_settings().dry_run` и `enable_auto_publish` **только в памяти процесса** и **не оставляли следа в логах**. Очевидно, кто-то из админов случайно включил `dry_run` после публикации 14 мая, и до перезапуска контейнера флаг так и держался.
- Корень причины 15.05: `faq`-item на 15 мая остался в `status=draft` (`generated_text`/`final_text`/`image_url` — `NULL`). Тип `faq` устойчиво ловился quality-гейтом `too_long`, и после пары попыток пайплайн оставил его в `draft`. Publisher фильтрует `status IN ('approved','ready')`, поэтому день оказался пустым, а исходный лог `publisher_run_empty` не объяснял, что в БД на эту дату вообще лежит и почему.

### Решение

## [2026-05-07] Спринт 3: воронка, аналитика и переход в боевой режим

### Наблюдения
- Реальный KIE Flux API живёт по адресу `POST /api/v1/flux/kontext/generate` + polling `GET /api/v1/flux/kontext/record-info?taskId=...`, а не `/v1/images/generations`, как было заложено в первой версии клиента; запросы возвращают `{code, msg, data: {taskId, successFlag, response: {resultImageUrl}}}`.
- DeepSeek `deepseek-chat` для info/sales-постов отрабатывает за 8-13 секунд на пост, KIE - за 21-59 секунд; полный недельный pipeline (3 поста с картинками) укладывается в ~2 минуты.
- `docker compose restart bot` НЕ перечитывает `.env`, нужен `up -d --force-recreate bot`. Это типовой грабли при ротации секретов.
- Воронку удобно строить на inline-кнопках Telegram: один callback - один сегмент. FSM не понадобился, потому что состояние читается из `lead_events` (последний segment пользователя).

### Решения
- Boevye ключи и Admin IDs живут только в `/opt/avaterra-bot/.env` (chmod 600, root:root); `Avaterra.pro.txt` теперь только справка без секретов.
- KIE-клиент полностью переписан под Flux Kontext API: модель по умолчанию `flux-kontext-pro`, обязательный `aspectRatio` из enum, парсим `successFlag` (0/1/2/3), берём картинку из `data.response.resultImageUrl`.
- Funnel router подключён ПЕРЕД admin router и не использует AdminOnly middleware: `/start` доступен всем, для админа отдаёт `admin_help`, для не-админа - запускает воронку.
- Сегменты воронки: `info` (читать материалы), `warm` (есть вопросы), `hot` (готов обсудить участие). Для `warm`/`hot` админам приходит уведомление с привязкой к Telegram-пользователю.
- Аналитика MVP сделана через ручной ввод `/stat <id> <views> [reactions] ...`: после публикации админу автоматически приходит подсказка с item_id. Авто-сбор views через MTProto - в Спринт 4.
- В `content_items` добавлены `tg_chat_id` и `tg_message_id`, чтобы будущий MTProto-collector смог сверять статистику без дополнительной таблицы маппинга.
- Включён `ENABLE_AUTO_PUBLISH=true` после успешного смоук-теста: ближайшая публикация - sales-пост в пятницу 11:00 МСК.

### Проблемы
- Картинки KIE имеют срок жизни 14 дней по их хосту `tempfile.aiquickdraw.com`. Для устойчивости нужен бэкап в S3 (планируется в Спринт 4).
- Авто-сбор статистики через Bot API невозможен (нет метода `getMessages`/`channelMessages`), поэтому `/stat` пока вводится вручную; на следующем шаге - подключить MTProto-сборщик в отдельном воркере.
- В одном сгенерированном sales-посте проскочило английское `maybe`. Это разовая галлюцинация модели, но стоит добавить в проверки фильтр на латиницу/одиночные английские слова (Спринт 4).
