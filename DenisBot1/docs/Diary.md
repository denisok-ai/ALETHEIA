# Avaterra Telegram SMM Bot - Project Diary

## [2026-05-07] Hotfix: битая ссылка `/store` и диагностика SSH-зависаний

### Наблюдения
- В повторно сгенерированном author-посте снова появилась ссылка `https://avaterra.pro/store`, которая на сайте отдает 404. При этом в `knowledge/avaterra.yaml` уже были корректные ссылки на курс и главную.
- Значит проблема не в KB, а в генерации: модель в части ответов «догадкой» подставляет путь `/store` по слову «каталог».
- Во время повторной публикации возникли массовые зависания `ssh/scp` из WSL-среды: процессы не завершались по таймауту и блокировали оперативные команды.

### Решения
- В `quality gates` добавлен контроль URL whitelist (`url_not_whitelisted`): разрешены только ссылки из `products`, `cta_library`, `quick_links`.
- В системный промпт добавлен жесткий запрет выдумывать URL и перечислен whitelist ссылок бренда.
- Обновлен KB: убраны упоминания `/store`, `catalog` перенаправлен на рабочие ссылки (`/course/navyki-myshechnogo-testirovaniya` и главная).
- Для операционной части введен runbook: чистка зависших `ssh/scp`, проверка `sshd`/fail2ban/ufw через веб-консоль, обязательный post-check контейнеров после деплоя.

### Проблемы
- Инцидент закрыт после перезапуска рабочей машины: SSH восстановился, деплой прошел, 4 поста успешно перепубликованы.
- Временные `publish_notify_failed` в логах при ручном скрипте остались ожидаемыми: параллельный экземпляр `Bot()` конкурирует с основным polling-процессом за уведомления админам, но сами публикации в канал проходят корректно.

### RCA (финал)
- Невалидная ссылка: генеративная галлюцинация URL в тексте (`/store`) при отсутствии жесткой URL-валидации.
- SSH-сбой: локальная рабочая среда накопила подвисшие `ssh/scp` процессы; после перезагрузки хоста и очистки процессов канал восстановился.

### Профилактика
- Ссылки: двойная защита (prompt whitelist + quality gate `url_not_whitelisted`).
- Публикация: минимальная задержка фото->текст enforced в коде (не ниже 5 секунд).
- Операции: для деплоя и диагностик использовать короткие команды с таймаутами и обязательным post-check `docker ps`/health.

## [2026-05-07] Hotfix: caption фото обрезался на 1024 символах

### Наблюдения
- После ручной публикации первых 4 постов администратор увидел в канале странное поведение: первое сообщение - картинка с подписью, оборванной на «Попробуйте сегодня простой шаг. К», и сразу следом второе сообщение с **полным** текстом от начала. Дубль первой части + всё равно нечитаемая подпись.
- Причина - старая логика `publish_item`: `send_photo(caption=text[:1024])` плюс `send_message(text)` если `len(text) > 1024`. Из-за этого первая часть текста дублировалась, а длинные посты (>1024 знаков) гарантированно ломали восприятие.

### Решения
- Картинка теперь идёт **без caption**, потом пауза `PUBLISH_TEXT_DELAY_SECONDS` (default 8 сек), потом полный текст одним `send_message`. `tg_message_id` сохраняем от ТЕКСТОВОГО сообщения - это объект для реакций и `/stat`.
- Под Telegram-лимит 4096 символов (на случай редких длинных постов) добавил `_split_text_for_telegram`: режет по абзацам, очень длинные абзацы - по символам. На сегодня все посты бренда укладываются в 1700 знаков, так что обычно это no-op.
- Новый параметр `PUBLISH_TEXT_DELAY_SECONDS` вынесен в `config.py` и `.env.example`, чтобы можно было крутить ритм без релиза.

### Проблемы
- Уже опубликованные 4 поста в канале остаются в старом формате (caption + дубль). Удалять/перепубликовывать их вручную - решение за владельцем канала.
- Отдельная картинка + текст создают визуальный «двойной пост» в канале, но при предпросмотре в превью канала Telegram схлопывает их в одно превью «фото + первая строка». В аналитике это будет два message_id, но `tg_message_id` мы фиксируем по тексту, так что метрики /stat ложатся правильно.

## [2026-05-07] Ручная публикация первых 4 постов недели

### Наблюдения
- После Спринта 4 в плане недели (2026-05-04 — 2026-05-10) был свежий контент, но публикации Mon/Tue/Wed уже прошли по календарю — `publish_due_today` их не подберёт (фильтр `publish_date = today`).
- Mon (educational) остановился на `text_ready` без картинки: сценарий, когда KIE-вызов в `prepare_item` не дошёл до конца (например, кратковременная сетевая ошибка), а текст уже был валиден.

### Решения
- Догенерировали картинку для Mon отдельным вызовом `generate_image_for_item` через `docker exec avaterra-bot python` (KIE Flux Kontext, ~47 секунд, backup сохранился локально как `file:///app/runtime/images/{item_id}.jpg`).
- Опубликовали все 4 поста (`Mon educational`, `Tue pain`, `Wed practice`, `Thu author`) одноразовым скриптом, который вызывает `publish_item` для каждого id с паузой 8 секунд между ними. Это сохранило идемпотентность и обновление статуса в БД.
- Все 4 item'a в БД переведены в `status='published'`, `tg_chat_id=-1003916704986`, `tg_message_id ∈ {5, 7, 9, 10}`, `published_at` проставлен.

### Проблемы
- В логах появилось `publish_notify_failed` для каждой публикации: основной aiogram-бот в polling держит сессию, второй временный экземпляр `Bot` не может отправить уведомление админам. Сами публикации в канал прошли успешно. На будущее: либо использовать долгоживущую `/publish_one <id>` команду внутри основного процесса бота, либо вынести запуск через Telegram (`/admin → План недели → опубликовать`).
- Эпизод подтвердил необходимость кнопки «Опубликовать» в карточке поста плана недели — это следующий слой UX-улучшений после Спринта 5 (выносить в Спринт 6).

## [2026-05-07] Спринт 5: Site Radar DoD + Telegram admin console

### Наблюдения
- Site Radar после Спринта 1.5 был «обходом ради обхода»: писал сигналы, но `theme_pool` строил с `post_type in {info, sales}`, который Спринт 4 уже не использовал. В реальной выдаче радара темы оседали в очередь и не подбирались планировщиком.
- Админу неудобно работать с `quality_failed` через CLI: нужно было копировать UUID из логов в `/preview`, понимать коды gates по логам, вручную сбрасывать статус в SQL.
- Веб-админка не вписывается в правила проекта (Python-only, без сайтов) и не нужна для пары админов - подтвердили в `docs/qa.md`.
- Метрика `noise < 5%` из Roadmap раньше нигде не считалась - нечего было сверять.

### Решения
- Дорожка A (Site Radar DoD):
  - `CycleStats` теперь явно считает `signals_high/medium/low`, `noise_blocks`, `noise_share`, `themes_rejected_dup`; метрики каждого цикла идут в `integration_logs` (`provider='site_radar'`) для долгосрочного аудита.
  - `strategist.build_theme` маппит сигналы радара на 7 типов AVATERRA + audience/rubric (`course/educational/faq/author`), темы попадают в `theme_pool` с `source='radar'` и теперь подбираются планировщиком тиерным фильтром.
  - Добавили `list_signals_audit` + команду `/radar_signals [high|medium|all] [page]` с inline-фильтрами и пагинацией; `/radar_now` показывает share шума и распределение severity.
- Дорожка B (Telegram admin):
  - `/admin` - inline-меню «План недели», «Очередь качества», «Радар», «Статус», тумблеры авто-публикации и dry_run.
  - `/quality_queue` показывает все `quality_failed` items с кодами последней неудачной gate-проверки; кнопка «↻ перегенерировать» вызывает `reset_item_for_regeneration` + `prepare_item`, кнопка «text» открывает полный отклонённый текст с кодами, «skip» помечает item как `failed`.
  - `AdminOnlyMiddleware` распространён на `CallbackQuery` (с alert «Доступ ограничен»).

### Проблемы
- Регенерация в админке выполняется в том же процессе/таске бота - на тяжёлых KIE-вызовах (60 сек) основной поллинг будет «тормозить». Если станет узким местом, вынесем в `BackgroundTasks` aiogram или в очередь воркера.
- `latest_quality_codes` сейчас опирается на формат `prompt_type LIKE '%_quality_%'` и `model_name='quality_gates'`. Если поменяется схема логирования в `text_generator`, нужно синхронизировать запрос.
- Вариант «пауза автопостинга» осознанно НЕ выносили в Redis/БД: тумблер `enable_auto_publish` в меню переживёт сессию, но не рестарт. Если потребуется persist, добавим колонку в `projects` отдельной задачей.

## [2026-05-07] Hotfix: Quality Gates обходились через image_generator

### Наблюдения
- При код-ревью Спринта 4 нашли критичный логический пропуск: `pipeline.prepare_item` короткое замыкание делал только для `dedup_status='blocked'`, а сценарий `quality_passed=False` шёл дальше в `generate_image_for_item`.
- `image_generator.update_item_image` пишет `status='ready'` без проверки текущего статуса, поэтому `quality_failed` молча превращался в `ready`.
- Публикатор берёт `final_text or generated_text`, а у quality_failed `final_text=NULL` (по дизайну) - значит в канал ушёл бы именно тот плохой `generated_text`.
- На проде смоук-тест Спринта 4 не триггерил баг только потому, что DeepSeek прошёл все gates с первой попытки.

### Решения
- Добавили в `pipeline.prepare_item` второй ранний выход - при `text_outcome.quality_passed is False` логируем `content_item_quality_failed` и возвращаем `PreparationOutcome(status='quality_failed', has_image=False)` без вызова KIE.
- Defense-in-depth в `image_generator.generate_image_for_item`: если `item.status in {quality_failed, dedup_blocked, failed}`, сразу возвращаем `ImageGenerationOutcome(skipped=True)` без обращения к KIE и БД.
- Поправили счётчик в `weekly_orchestrator`: `quality_failed` считается как `blocked`.
- Регрессия закрыта 4 тестами (`test_pipeline_quality_gate.py`).
- Прод-смоук с stub-DeepSeek: `db.status` корректно остался `quality_failed`, `published_at=NULL`, KIE не дёрнулся.

### Проблемы
- Урок процесса: интеграционный тест "fail-path" не проверялся в Спринте 4 - только happy path. На будущее перед сдачей фичи нужен явный adversarial тест на каждый gate.
- Не делали retry quality_failed в weekly_orchestrator - админ должен сам решать. Если будем видеть много quality_failed, вернёмся к авто-ретраю с расширенным feedback.

## [2026-05-07] Спринт 4: Brand DNA, Quality Gates и 7 постов в неделю

### Наблюдения
- Без жёсткой бренд-DNA модель легко уходит в обещания «вылечим/гарантируем» и в эзотерический жаргон. Нужны явные запретные формулировки.
- В KB.md от заказчика 7 типов постов и 30-дневная сетка, что плотнее текущего ритма 3/неделю - подтверждено `go_7`.
- KIE отдаёт временные ссылки (~14 дней) и без бэкапа канал теряет картинки в архиве.
- Tone of Voice описан несколькими блоками (TOV do/don't, безопасные замены, дисклеймер) - все они должны жить в одном источнике истины, иначе будут рассинхрон.
- При деплое контейнер успел стартовать ДО применения миграций - бутстрап KB упал на отсутствующих колонках. После рестарта поднялся.

### Решения
- Сделали `knowledge/avaterra.yaml` единой истиной для бренда, продуктов, рубрик, шаблонов, CTA, запрещённых фраз, безопасных замен и дисклеймера. Версия фиксируется через SHA-256 первых 16 символов.
- Расширили `brand_profiles` 12 JSONB-полями + `kb_version`; YAML грузится автоматически на старте бота и по `/kb_load`.
- 7 типов постов закрыли через миграцию 009 (расширили CHECK для `content_items` и `theme_pool`, добавили `theme_pool.source/audience/rubric`).
- Quality gates (5 проверок) встроены в `text_generator` с до 2 повторов и фидбеком в user prompt; на провале статус `quality_failed`, в `prompts.error_code` записан список codes.
- Бэкап картинок: `boto3` если есть S3-ключи, иначе локальный `/app/runtime/images` (volume `bot_runtime`); `channel_publisher` публикует backup, `file://` оборачивает в `FSInputFile`.
- Подбор темы в планировщике трёхуровневый: `(post_type+rubric+audience)` -> `(post_type+rubric)` -> `(post_type+audience)` -> `(post_type)`; при пустом результате fallback из in-code-словаря.
- Cron публикатора динамический: `mon,tue,wed,thu,fri,sat,sun` при `POSTS_PER_WEEK>=7`, иначе старый `mon,wed,fri`.
- На проде сбросили старые планы/посты, чтобы планировщик сразу собрал свежий 7-дневный план.

### Проблемы
- Картинки KIE без HTTP-кеша на нашей стороне устаревают - временно решили локальным backup, в будущем стоит включить S3 (вопрос вынесен в qa).
- В YAML 30 тем, но рубрика «practice» представлена 2 темами - нужно расширить theme_bank в Спринте 5.
- Вопрос с MTProto-сборкой статистики окончательно закрыт: не используем, остаёмся на ручном `/stat` по подсказке после публикации.
- Если KIE-картинка вернётся медленно (>180с), мы не блокируем публикацию: пишем `image_backup_status='failed'` и публикуем оригинальный URL - это поведение задокументировано.

## [2026-05-07] Спринт 0: каркас, инфра, логи, бэкапы, антидубли

### Наблюдения
- Чтобы не накапливать тех. долг, сразу заложили минимальный production-grade каркас.
- Антидубли реализованы как самостоятельный модуль с явным контрактом, чтобы интегрировать его в pipeline в Спринте 1 без переделок.

- Стек: Python 3.12 + aiogram 3 + Postgres 16 + Redis 7 + Docker compose.

- Антидубли: SHA-256 (жесткий блок) + MinHash 128 perm на шинглах из 5 слов + ключевые слова с порогом Жаккара 0.7.
- Деплой: rsync + remote `docker compose up -d --build` с pre-deploy backup и rollback через `restore.sh`.

### Проблемы
- Удаленный сервер еще не подготовлен (нет SSH-ключа агента, пароль ротируется).
- Нужно подтвердить целевой timezone проекта, чтобы корректно сконфигурировать scheduler.
- Реализация интеграции антидублей в pipeline отнесена к Спринту 1 - чтобы не дробить контекст.

## [2026-05-07] Спринты 1+2 в dry-run на проде: автономный pipeline собран

### Наблюдения
- DeepSeek и KIE - простые HTTP-клиенты; KIE требует polling задачи (~3-180 с в зависимости от модели).
- Темы `theme_pool` от Site Radar сразу подходят для `info`-постов (про блог, FAQ, about), но `sales` нужно подкреплять fallback-темами курсов, иначе план тривиализируется.
- Общий pipeline (план + 3 поста + картинки) в dry-run выполняется за < 200 мс - вся задержка на проде уйдёт в DeepSeek/KIE.
- Один общий `AsyncIOScheduler` в процессе бота держит 4 задачи: site_radar_full, site_radar_priority, content_planner_weekly, content_publisher_daily.

### Решения
- Включён `DRY_RUN=true` и `ENABLE_AUTO_PUBLISH=false` по умолчанию: ничего не уйдёт в канал, пока админ явно не переключит.
- Антидубли применяются дважды: на этапе подбора темы (`is_duplicate_topic` в Planner) и на тексте после генерации (`DuplicateChecker.check`).
- Промпт-инжиниринг закреплён в коде (`services/generator/prompts.py`) - структура info/sales, общие правила, негативные правила для картинок.
- Все вызовы DeepSeek/KIE/Telegram логируются в `integration_logs` c `request_id`, в `prompts` - тип/модель/латентность/статус.
- Добавлен UNIQUE индекс `projects(website_url)` (миграция 007), чтобы рестарты бота не плодили дубликаты проектов.

### Проблемы
- Без реальных ключей DeepSeek/KIE pipeline работает только в dry-run - тексты заглушечные. Нужны рабочие ключи (DEEPSEAK_API_KEY, KIE_API_KEY) и переключатель `DRY_RUN=false` для боевого запуска.
- ADMIN_TELEGRAM_IDS пуст - admin-команды (`/plan`, `/preview`, `/approve`, `/dry_run`) пока недоступны.
- При первом запуске на проде остался артефакт: `DuplicateChecker.__init__` ожидал `keyword_threshold`, а я передавал `keyword_overlap_threshold` - поправлено и подтверждено повторным прогоном.
- Картинки сейчас используют URL от KIE напрямую; для долгосрочного хранения и устойчивости нужен бэкап в S3 (отложено).

## [2026-05-07] Спринт 3: воронка, аналитика и переход в боевой режим

### Наблюдения
- Реальный KIE Flux API живёт по адресу `POST /api/v1/flux/kontext/generate` + polling `GET /api/v1/flux/kontext/record-info?taskId=...`, а не `/v1/images/generations`, как было заложено в первой версии клиента; запросы возвращают `{code, msg, data: {taskId, successFlag, response: {resultImageUrl}}}`.
- DeepSeek `deepseek-chat` для info/sales-постов отрабатывает за 8-13 секунд на пост, KIE - за 21-59 секунд; полный недельный pipeline (3 поста с картинками) укладывается в ~2 минуты.
- `docker compose restart bot` НЕ перечитывает `.env`, нужен `up -d --force-recreate bot`. Это типовой грабли при ротации секретов.
- Воронку удобно строить на inline-кнопках Telegram: один callback - один сегмент. FSM не понадобился, потому что состояние читается из `lead_events` (последний segment пользователя).

### Решения
- Boevye ключи и Admin IDs живут только в `/opt/avaterra-bot/.env` (chmod 600, root:root); `Avaterra.pro.txt` теперь только справка без секретов.
- KIE-клиент полностью переписан под Flux Kontext API: модель по умолчанию `flux-kontext-pro`, обязательный `aspectRatio` из enum, парсим `successFlag` (0/1/2/3), берём картинку из `data.response.resultImageUrl`.
- Funnel router подключён ПЕРЕД admin router и не использует AdminOnly middleware: `/start` доступен всем, для админа отдаёт `admin_help`, для не-админа - запускает воронку.
- Сегменты воронки: `info` (читать материалы), `warm` (есть вопросы), `hot` (готов обсудить участие). Для `warm`/`hot` админам приходит уведомление с привязкой к Telegram-пользователю.
- Аналитика MVP сделана через ручной ввод `/stat <id> <views> [reactions] ...`: после публикации админу автоматически приходит подсказка с item_id. Авто-сбор views через MTProto - в Спринт 4.
- В `content_items` добавлены `tg_chat_id` и `tg_message_id`, чтобы будущий MTProto-collector смог сверять статистику без дополнительной таблицы маппинга.
- Включён `ENABLE_AUTO_PUBLISH=true` после успешного смоук-теста: ближайшая публикация - sales-пост в пятницу 11:00 МСК.

### Проблемы
- Картинки KIE имеют срок жизни 14 дней по их хосту `tempfile.aiquickdraw.com`. Для устойчивости нужен бэкап в S3 (планируется в Спринт 4).
- Авто-сбор статистики через Bot API невозможен (нет метода `getMessages`/`channelMessages`), поэтому `/stat` пока вводится вручную; на следующем шаге - подключить MTProto-сборщик в отдельном воркере.
- В одном сгенерированном sales-посте проскочило английское `maybe`. Это разовая галлюцинация модели, но стоит добавить в проверки фильтр на латиницу/одиночные английские слова (Спринт 4).
