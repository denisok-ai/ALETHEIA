## Что есть в коннекторах (интерфейс для VK)

Из `lib/social/connectors/telegram.ts`, `max.ts`, `publish-error.ts`, `scheduler.ts`:

- Коннектор экспортирует `publishVideo({ chatId, filePath, caption })` и `publishText({ chatId, text })`, возвращает `{ messageId, url }`. Планировщик хранит `externalId` как строку (`String(messageId)`).
- `SocialPublishError` с полями `kind`, `ambiguous`, `retryAfterSec`:
  - `kind: 'flood'` — планировщик не засчитывает попытку, пост ждёт следующего прохода (`held`);
  - `ambiguous: true` — запрос ушёл, ответ потерян → пост в `failed`, автоповтора нет, алерт владельцу «проверьте канал»;
  - прочие ошибки — `attempts+1`, до 3 попыток, затем `failed`; две ошибки подряд в сети выключают сеть.
- В `scheduler.ts` `CONNECTORS = { telegram, max }`, VK в него нужно добавить, а в `PLATFORM_NAMES` дописать название. Сейчас для `mode='auto'` сеть без коннектора получает `held: нет коннектора`.
- Шаблон для VK по структуре ближе к MAX: несколько шагов (загрузка → публикация), один шаг с возможной обработкой «видео ещё не готово» (`not_ready`-подобный, повтор с паузами), и только последний шаг (создание записи на стене) — `ambiguous` при сетевом сбое.

## 1. Токен для публикации в стену сообщества

**Ответ (частично подтверждён):**

- **[подтверждено, Habr/skills.sh]** Для `wall.post` от имени сообщества нужен **ключ доступа сообщества** с правом `wall` (ошибка 214 = у токена нет права на стену). Вызов: `owner_id` = отрицательный id сообщества, `from_group=1`.
- **[подтверждено, Habr]** Сообщают, что `wall.post` с **сервисным** ключом отклоняется («method is unavailable with service token»). Сервисный ключ не использовать.
- **[подтверждено, Habr, есть противоречивые сообщения]** Ключ сообщества с правами `wall` иногда не работает для `wall.post` (Access denied, error 15). Вопрос «почему ключ, созданный в сообществе, не подходит» остался без принятого ответа. Причина в выборе типа приложения или в правах ключа — **не выяснено**. Нужна проверка руками.
- **[из памяти, не проверено]** `video.save` с `group_id` и `photos.getWallUploadServer` для сообщества работают с ключом сообщества при праве `video` / `photos` соответственно. Права выдаются при создании ключа в настройках сообщества → «Работа с API».

**Ограничения:**
- [подтверждено, Habr] Пользовательский токен с `wall` тоже работает, но его жизнь короче и привязана к человеку-администратору.
- [из памяти] Ключ сообщества не даёт вызовов от имени пользователя и методов, требующих `groups.edit`-подобных прав (менеджеры, настройки).

**Вывод:** основной вариант — ключ доступа сообщества с правами `wall`, `video` (и `photos`, если будем постить фото). Резервный — пользовательский токен администратора. Если ключ сообщества не даёт `wall.post` (ошибка 15) — переходим на пользовательский токен администратора.

## 2. Вертикальное видео как Клип VK

**Подтверждено (статья VK «Клипы для сообществ», vk.ru/@adminsclub-clips-for-communities):**
- Формат строго вертикальный, рекомендуется 9:16, 1080×1920.
- Длительность: от 5 секунд до 3 минут (наш ролик 20–30 с подходит).
- Публикация клипа от имени сообщества описана **только через мобильное приложение**: раздел «Клипы» → «Снять»/«Загрузить» → на последнем шаге выбрать сообщество. Про публикацию клипов через API в статье **ничего нет**.
- Коммерческим сообществам нельзя использовать треки из библиотеки клипов (на музыку в роликах обратить внимание, у нас в роликах её быть не должно).

**Что с API — [неизвестно]:**
- Нет подтверждённого метода или параметра «клип» в `video.save`. Найденные материалы описывают обычный путь: `video.save` (с `group_id`, `name`, опционально `wallpost=1`) → загрузка файла на `upload_url` → видео появляется в видео сообщества. Пометить видео как клип через API — **не найдено**.
- Вывод: **безопасный вариант — публиковать ролик как обычное видео на стене через API** (`video.save` + загрузка + `wall.post` с `attachments=video{owner}_{id}`). Клип в смысле «лента клипов» — ручной шаг владельца в приложении (см. ниже), пока не проверено, что API это умеет.

**Лимиты размера/длительности для API-видео:** в найденных источниках не указаны. [из памяти] Для обычного видео лимит по размеру большой (порядка единиц ГБ), но для нашего ролика 20–30 с мб ~ 10–30 МБ, это не проблема. Точное значение — проверить.

## 3. Пользовательский токен без серверного OAuth

**Найдено (слабые источники):**
- [Habr, вопрос 1388884 и др.] Старый implicit flow через `oauth.vk.com` и «Standalone-приложение» — сообщают, что сейчас уже не работает или работает с ограничениями; новые приложения идут через **VK ID (id.vk.ru / id.vk.com), OAuth 2.1, PKCE, `device_id`**.
- [сторонний README `gam6itko/oauth2-vk-id`, Packagist] Провайдер VK ID: PKCE (S256), `device_id` приходит в callback и нужен при обмене кода на токен, эндпоинты `id.vk.ru`. Это подтверждает схему, но не сроки жизни.
- [Habr, один пост] `refresh_token` есть, `expires_in` в примере 86400 с (24 ч) у access-токена; флаг `offline` в одном посте «отключён» (запрос с `offline` и `video` даёт ошибку). Единичные свидетельства, не официальные.
- [из памяти, не проверено] Старые пользовательские токены standalone-приложений выдавались с `expires_in=0` (бессрочно) при запросе со scope `offline`. Сейчас это изменилось — проверить.

**Вывод:** для нашего сценария (публикация с сервера раз в день) **не полагаться на бессрочный токен**. Схема: один раз администратор проходит VK ID авторизацию (PKCE) с нужными scope → сохраняем access + refresh в зашифрованных настройках портала → перед публикацией обновляем access по refresh (если refresh есть). Если refresh-токена нет — раз в N недель владелец заново проходит авторизацию.

**Сроки жизни:** [неизвестно, нужно проверить] (ответ VK по `expires_in`, наличие `refresh_token` без `offline`, ротация refresh-токена).

**Лучший вариант для сообщества — ключ доступа сообщества.** Он создаётся в настройках сообщества и не истекает (по общему опыту, [из памяти, не проверено]), не требует VK ID-авторизации и обновления. Поэтому пользовательский токен — только резервный вариант.

## 5. Метка `?ref=vk-NN` в ссылке и превью

- [подтверждено по коду проекта] Ссылки с меткой строятся через `trackedUrl(base, refCode)` (`lib/social/refs.ts`), Telegram и MAX получают `disable_web_page_preview: false` / превью по умолчанию. Для VK то же: текст поста содержит ссылку с меткой.
- [из памяти, не проверено] В `wall.post` превью ссылки делается через параметр `attachments` с типом `link` (`attachments=https://avaterra.pro/...?ref=vk-NN`). VK сам подтягивает og-картинку из страницы (у нас OG-карточки `/api/og/` разрешены в robots.txt — см. CLAUDE.md проекта). Если нужно строго — передаём `attachments` отдельным `link`-элементом; при наличии видео в `attachments` ссылка добавляется отдельным элементом только если VK это допускает (проверить: одновременно видео + ссылка в одном посте, как правило, допускается до 10 вложений).
- Метка `ref=vk-NN` — в самом URL, VK её не трогает. Проверить, что VK не переписывает внешние ссылки (сокращает через `vk.cc`) — если переписывает, ref-метка теряется в лог-ссылке; в тексте ставить полный URL с меткой.

## Рекомендуемая схема

**Токен:** ключ доступа сообщества (права `wall`, `video`, `photos`), хранится в настройках портала (зашифровано, как `max_bot_token`), переменная окружения `VK_GROUP_TOKEN` — по аналогии с MAX.
**Идентификатор:** `VK_GROUP_ID` (число, без минуса), в вызовах `owner_id = -GROUP_ID`.
**API версия:** параметр `v` — последняя актуальная (проверить на dev.vk.com; версии VK обновляются).

**Ролик (`publishVideo`):**
1. `video.save` с `group_id=GROUP_ID`, `name` = заголовок, `description` = подпись, `wallpost=0` (сами создадим пост);
2. POST-загрузка файла на `upload_url` (multipart, поле `video_file`);
3. ожидание обработки (VK присылает видео «в обработке» некоторое время; как проверять готовность — `video.get` по `owner_id`/`video_id`, проверить);
4. `wall.post` с `owner_id=-GROUP_ID`, `from_group=1`, `message=подпись`, `attachments=video{owner_id}_{video_id}` (и `link`, если нужен отдельный превью).
5. Результат: `post_id` → `externalId`, URL `https://vk.com/wall-{GROUP_ID}_{post_id}`.

Клип в ленте клипов — **ручной шаг** (см. владельца), пока не доказано, что API умеет клипы.

**Текст (`publishText`):** один вызов `wall.post` с `from_group=1`, `message=текст`, `attachments=link` (ссылка с меткой). Одношаговый, проще всего.

**Ошибки:**
- `flood` (6, 9) → `flood` в `SocialPublishError` (с `retryAfterSec` ~ 60–300 с), попытка не засчитывается.
- Шаги 1–2 (загрузка) → обычные ошибки, в сообщество ничего не ушло, попытка засчитывается.
- Шаг 4 (`wall.post`) с сетевым сбоем или 10 → `ambiguous: true`.
- Коды 5, 15, 203, 214, 100 → постоянные, сеть выключится через две ошибки, владелец проверяет токен.

## Риски

- **Официальная документация не проверена.** Главный риск: коды ошибок, права ключа, `video.save` для сообщества и лимиты — из памяти и сторонних источников. Обязательно сверить на dev.vk.com перед кодом.
- **Клипы через API не подтверждены.** Вероятно, придётся публиковать обычным видео; раздел «Клипы» — ручной шаг.
- **Ключ сообщества не даёт `wall.post` (ошибка 15)** — по Habr-вопросам это бывает. Тогда переход на пользовательский токен, который живёт меньше и требует обновления.
- **Пользовательский токен и OAuth:** implicit и standalone-схемы, судя по источникам, устарели; VK ID PKCE — актуальный путь, сроки жизни неизвестны.
- **Дубли при сбое:** `wall.post` без автоповтора по аналогии с Telegram/MAX; при сбое владелец проверяет стену.
- **Видео в обработке:** если VK не готов к `wall.post` сразу после загрузки, нужна пауза и повтор (аналог `not_ready` у MAX); как VK сигнализирует — проверить.
- **Политика:** музыка из библиотеки клипов для коммерческих сообществ запрещена (см. статью VK) — в роликах школы музыки не использовать без проверки.
- **Ссылки:** возможна переписка ссылок VK → проверить, что метка `ref=vk-NN` сохраняется в ссылке поста.
