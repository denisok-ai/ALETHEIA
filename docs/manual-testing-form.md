# Форма проведения тестирования и обратной связи (AVATERRA)

Документ задаёт **как проводить прогон**, **как фиксировать результаты** и **как описывать баги**, чтобы исправление шло без лишних уточнений. Список проверок — в [`manual-qa-checklist.md`](./manual-qa-checklist.md).

---

## 1. Титул прогона (заполняется в начале сессии)

| Поле | Значение |
|------|----------|
| Дата | |
| Тестировщик | |
| Окружение | прод / стенд / локально |
| Базовый URL | |
| Сборка / коммит (если известно) | |
| Ветка / релиз | |

**Цель прогона** (выбрать или указать):

- [ ] Полный чек-лист
- [ ] Дымовой прогон (критичные пути)
- [ ] Регрессия после релиза / PR
- [ ] Проверка одной фичи: _______________

---

## 2. Краткий статус по ролям

После прогона отметить итог (можно одной фразой в ячейках):

| Роль | Статус | Замечания |
|------|--------|-----------|
| Гость | OK / есть баги | |
| Студент | OK / есть баги | |
| Менеджер | OK / есть баги | |
| Администратор | OK / есть баги | |

---

## 3. Таблица учёта по разделам чек-листа

Используйте при полном прогоне. Статусы: **OK**, **N/T** (не тестировалось), **BUG** (есть дефект — заполнить блок §4).

| Раздел чек-листа | Статус | № бага (ссылка) |
|------------------|--------|-----------------|
| A. Гость | | |
| B. Студент | | |
| C. Менеджер | | |
| D. Админ | | |
| E. Сквозные сценарии | | |

---

## 4. Шаблон сообщения о дефекте (баг)

Скопируйте блок ниже **на каждый** найденный баг (issue, Telegram, почта — куда принято в команде).

```
────────────────────────────────────────
ID / №: T-___   (присвоить вручную при учёте)

Тип: [ ] баг  [ ] непонятный UX  [ ] идея  [ ] текст/контент  [ ] безопасность

Кратко (одна строка):


URL:


Роль: [ ] гость  [ ] студент  [ ] менеджер  [ ] админ


Шаги воспроизведения:
1.
2.
3.


Ожидалось:


Получилось:  (текст ошибки с экрана — целиком, если есть)


Стабильность: [ ] всегда  [ ] иногда (как часто: ___)


Окружение:
- Браузер и версия:
- Устройство (ПК / телефон, примерно разрешение):
- ОС:


Вложения: [ ] скриншот  [ ] короткое видео  [ ] нет

Срочность (субъективно):
[ ] блокер (оплата / обучение / потеря данных)
[ ] важно
[ ] можно позже
────────────────────────────────────────
```

### Критерии хорошего описания

- Есть **точный URL** и **роль** — иначе часто нельзя воспроизвести RBAC и маршруты.
- **Шаги** — нумерованный список «нажал А → нажал Б».
- **Ожидалось / получилось** — явный критерий «когда починим — станет OK».

---

## 5. Шаблон «идея / улучшение» (не баг)

```
Тип: улучшение

Где (URL / раздел):


Сейчас как:


Предлагаю:


Зачем пользователю / бизнесу:
```
